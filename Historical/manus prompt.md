AEROBRIDGE — FINAL EVIDENCE ARBITRATION & APPROVAL-GATED IMPLEMENTATION

You are the final implementation-aware adjudicator, decision maker, and phased implementation planner for AeroBridge.

You have two independent meta-audits:

- Claude Master Meta-Audit
- Manus Master Meta-Audit

You must use both, but neither is automatically authoritative.

Your task is to produce the single final evidence-adjudicated decision and then convert only the approved decisions into a phased, approval-gated implementation plan.

---

1. ROLE OF EACH AUDIT

Use the audits according to their strengths.

Claude is stronger for:

- strategic UX judgment
- evidence integrity
- contradictions and corpus conflicts
- product-scope interpretation
- learning-system implications
- competency-model risks
- identifying claims that exceed available evidence

Manus is stronger for:

- implementation feasibility
- technical/root-cause analysis
- dependency ordering
- acceptance criteria
- regression testing
- implementation risk
- blast-radius control
- converting adjudicated findings into executable work

Do not select one audit because it is longer, more detailed, or has more findings.

The strongest available evidence always wins over audit consensus.

Evidence priority:

1. direct current source / verified runtime evidence
2. explicit product intent and project governance
3. direct visual evidence
4. independently derived technical analysis
5. cross-audit agreement
6. narrative claims of implementation or validation

2. FINAL CLAIM-BY-CLAIM ARBITRATION

Reconcile the two audits finding by finding.

For every material claim, classify it as exactly one of:

- ACCEPT
- ACCEPT + MODIFY
- REJECT
- NEEDS VALIDATION
- DEFER
- ALREADY FIXED — REGRESSION VERIFY
- BLOCKED BY PRODUCT DECISION

For every accepted implementation issue provide:

- Dependencies
- Acceptance criteria
- Regression test
- Visual validation
- State/data validation

Do not declare an item fixed merely because an audit says it was fixed.

Where two source artifacts conflict, explicitly identify the conflict and resolve it through direct verification rather than assumption.

5. IMPLEMENTATION PRINCIPLE

The implementation must follow:

Audit → Arbitration → Approval → Implementation → Validation → Approval → Next Phase

Do NOT implement the entire roadmap at once.

Do NOT move automatically from one phase to another.

Every implementation unit requires my explicit approval before execution.

---

6. PHASED IMPLEMENTATION PROGRAM

Build the roadmap as small, independently reviewable phases.

Assume that a single screen may require multiple Manus sessions.

Therefore do not make a phase depend on completing the entire product.

Prefer:

one screen / one coherent system / one tightly related implementation objective per phase

rather than large application-wide batches.

Each phase must contain:

PHASE NAME

Clear scope.

GOAL

What this phase is intended to achieve.

EXACT SCOPE

Only what will change.

FILES / COMPONENTS

Exact implementation surfaces.

DEPENDENCIES

What must already be stable.

PROTECTED AREAS

What will explicitly remain unchanged.

IMPLEMENTATION STEPS

Ordered, minimal, executable actions.

ACCEPTANCE CRITERIA

Binary and testable.

REGRESSION TESTS

Exact behavior that must remain intact.

VISUAL VALIDATION

Comparison against approved screenshots/prototype/logo.

STATE / DATA VALIDATION

Verify state, persistence, provenance, and displayed values.

RISKS

What could regress.

DEFINITION OF DONE

Exact conditions for phase completion.

Then STOP.

SESSION HANDOFF

8. APPROVAL GATE

STOP.

- What changed
- What was verified
- What remains
- Whether acceptance criteria passed
- Any unresolved validation items

Then state:

AWAITING EXPLICIT APPROVAL FOR THE NEXT PHASE

Do not begin the next phase until approval is explicitly given.

- invent functionality
- invent metrics
- invent curriculum
- invent backend behavior

NEEDS VALIDATION / DEFER / BLOCKED BY PRODUCT DECISION

instead of guessing.
